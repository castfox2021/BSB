# 신호 자동매매 · 페이지 이력

기준 2026-11-11. 사용자 요청으로 화면 직접 주문에서 자동매매를 추가했다. 개발 중 AI 에이전트가 실계좌 자동매매를 활성화하거나 실제 주문을 보내지는 않는다. 기본 정지이며 사용자가 앱에서 한 번 활성화한 세션만 자동 실행한다.

## 승인과 실행

자동매매 시작 시 새 로컬 키·Private 연결·잔고/체결 복구·최초 원장 대조·비용 확인·검증 및 승인된 실전 전략·고정 매수 예산을 확인한다. 사용자는 주문하기 권한을 확인하고 ‘신호에 따라 실제 자동매매를 시작합니다’ 문구로 시작한다. 권한 확인은 사용자 확인 항목이며 앱이 조회 API로 실제 주문 권한을 사전 입증했다는 뜻은 아니다. 주문 권한 거절은 세션을 정지한다. 환경변수나 단순 AUTO_APPROVAL 모드 선택으로 시작하지 않는다.

시작한 전략 버전을 고정하고 BUY_CANDIDATE만 자동 매수한다. WATCH_ENTRY와 실험 버전은 제외한다. 전략 원장의 SELL_CANDIDATE/RISK_EXIT는 보유 수량 안에서 자동 매도한다. 기존 전략 원장 보유분도 자동 청산 신호의 대상이다. 계좌 전체 외부 보유분을 자동 편입하지 않는다. 활성화 전 신호·만료 신호·승인되지 않은 버전은 실행하지 않는다.

전략 변경이나 검증 유효기간/비용 조건 미충족은 신규 매수를 막는다. 기존 보유분의 위험 청산 신호는 유효한 시세와 계좌 조건 아래 계속 처리한다. 매도·손절을 매수보다 우선하며, 자동 추가 매수와 손실 만회 증액은 없다. 같은 종목의 자동 재진입은 60초 대기한다. 매수 예산·운용 자본·손실 기준·현금 여유·포지션 제한은 기존 서버 검사와 동일하다. 시장가 가격/수량·최대 손실을 보장하지 않는다.

## 중복·정지·재시작

SQLite schema 5의 auto_signal_claims에 (로컬 계정 영역, signal_id) 고유 키로 실행을 먼저 예약한다. 주문 ID를 같은 트랜잭션으로 연결하고, 기존 직접 주문 실행기의 SUBMITTING/UNKNOWN 영속 상태와 cross-process write fence를 재사용한다. 같은 신호는 연결 복구·반복 수신·재시작 후 재전송하지 않는다. 전송 중 성공 여부를 모르면 기존 ID로 조회하며 새 주문으로 재시도하지 않는다.

자동 실행은 내부 객체 권한을 사용한다. 웹의 직접 주문 경로는 활성 자동매매 권한을 사용할 수 없으며 자동 실행 중 직접 주문을 차단한다. 전송 직전에 정지·세션·신호 만료·전략·위험 조건을 다시 검사한다. 정지 시 대기 중 시도를 취소하고, 이미 전송됐을 수 있는 주문은 SUBMITTING/UNKNOWN을 유지해 조회로 확인한다. 전송 취소나 HTTP 연결 종료를 거래소 주문 취소로 간주하지 않는다.

재시작은 항상 정지 상태다. 남은 PREVIEW는 만료시키고 중단된 신호 예약을 보존한다. 이전 SUBMITTING/ACKNOWLEDGED/UNKNOWN은 조회로 복구한다. 브라우저를 닫아도 서버가 살아 있으면 실행한다. 노트북 절전·인터넷 중단 동안 손절은 보장할 수 없다. 사용자 정지·긴급 정지는 이미 접수된 주문 취소나 강제 청산을 수행하지 않는다.

## 원장과 결과

실제 체결 ID·가격·수량·수수료로 전략 원장을 갱신한다. 자동매매 자체 체결은 최초 승인한 계좌 기준 안에서 대조 승인을 반복 요구하지 않는다. 외부 체결은 이를 우회하지 못하고, 실제 현금/보유 수량 검사는 유지한다. 수수료의 정확한 값이 뒤늦게 도착하면 원장을 보정한다. 매도 실현 손익은 전체 체결 원가를 기준으로 계산하며 접수 응답을 손익으로 계산하지 않는다.

화면 상단에 실제 체결 결과·수수료·실현 순손익을 표시한다. 새 체결 시 화면 상태 메시지와 사용자가 이미 허용한 브라우저 알림/소리로 알린다. 브라우저가 닫혀 있으면 화면/소리 알림을 보장하지 않는다. 주문 상태와 자동매매 활동 로그는 접힌 상세 영역에 별도로 기록한다. 결과 불명·거절 시 자동매매가 정지하며 원문 API 오류/키/토큰은 표시하지 않는다.

## 이력 API

GET `/api/history/{signals|orders|trades|journal|private-orders|automation}`

- page: 1 이상, page_size: 1~50 (화면 기본10, 선택10/20/50)
- before: 서버가 돌려준 조회 스냅샷, journal은 선택 day=YYYY-MM-DD(KST)
- 응답: items, total, page, page_size, pages, snapshot
- 과거 페이지는 시각과 삽입 rowid 상한을 고정한다. 새 거래 및 뒤늦게 수집한 과거 내역이 이전 페이지를 밀지 않는다. 같은 시각은 고유 ID로 안정 정렬한다.
- 거래 손익은 전체 원장 계산 후 결과를 분할한다. 개별 페이지를 독립 원장으로 계산하지 않는다.
- 사설 이력은 로컬 계정 영역으로 제한하고 키·주문 서명 파라미터·세션 권한을 노출하지 않는다.

GET `/api/automation/status`, POST `/api/automation/activate`, POST `/api/automation/stop`은 기존 로컬 Host/Origin/JSON 헤더 검사를 따른다. 시작은 승인 문구·버전·예산·권한 확인이 필요하다. 정지는 대기 작업 락을 기다리지 않고 즉시 새 전송을 막는다.

## 검증

가짜 키·MockTransport·로컬 WebSocket으로 자동 매수/매도·실제 체결 원가·미승인/관찰/만료 신호 제외·중복 수신·손실/계좌/버전 차단·불명 응답·정지·재시작·자체/외부 체결 구분을 확인한다. 이력은 200건 초과 조회·동일 시각·늦은 삽입·계정 분리·날짜 필터·전체 원가 보존을 검사한다. 실계좌 자동 주문은 개발 검증에 사용하지 않았다. 실제 계좌 및 주문 권한·체결의 운영 검증은 아직 별도다.

공식 계약: [주문 요청](https://apidocs.bithumb.com/reference/주문-요청), [개별 주문 조회](https://apidocs.bithumb.com/reference/개별-주문-조회). 기존 GET 조회 클라이언트와 별도 POST 주문 전송기는 동일 JWT 직렬화 계약을 사용한다.
