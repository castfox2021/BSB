# 화면 직접 매수·매도 — 수동 확인 주문

2026-11-11. 최신 사용자 요청에 따라 이전 ‘설계만 포함, 전송 차단’ 범위를 변경했다. **사용자가 이 앱에서 종목과 주문 내용을 확인하고 최종 전송 버튼을 누르면** 실제 빗썸 주문을 전송한다. 신호 기반 자동 주문·자동 승인 실행·취소·출금은 없다. AI 에이전트는 개발 중 실제 키로 활성화/주문을 수행하지 않는다.

## 운영

새 키는 권한 600의 루트 `.env`에서만 읽는다. 노출된 키는 폐기·재발급해야 한다. Private API 연결·잔고·체결 복구가 정상이고 사용자가 계좌/전략 원장을 대조한 다음 화면에서 ‘실제 매수·매도를 직접 확인합니다’ 문구로 수동 실주문을 활성화한다. 재시작 시 항상 정지한다. 환경변수 `LIVE_ORDER_ENABLED`로 활성화할 수 없다. 주문 권한은 거래소에서 부여해야 하며 실제 요청이 `out_of_scope`로 거절되면 세션을 정지한다. 활성화 자체가 거래소 주문 권한을 검증했다는 뜻은 아니다.

시장 탭의 관심 종목 또는 신호에서 종목/방향을 선택한다. 직접 입력도 가능하다. 매수는 수수료 포함 예산(최대 50,000원), 매도는 전략 수동 원장과 실제 계좌 모두에 있는 수량을 입력한다. 서버가 조건을 검사하고 30초 유효한 확인 내용을 저장한다. 사용자가 체크박스를 선택하고 해당 주문의 실제 전송 버튼을 눌러야 전송한다. 신호 만료 또는 가격이 불리하게 0.3% 초과 변화하면 재확인을 요구한다.

직접 주문은 전략 승격을 요구하지 않는다. 관찰 매수 신호는 완료 1분봉 상승·직전 종가 상향·평균 이상 거래량을 참고하며 미검증 관찰용으로 표시한다. 기존 검증된 전략 신호와 구분한다. 전략 엔진은 주문 전송 함수를 호출하지 않는다. 모든 POST는 사용자 확인 경로만 사용한다.

## 위험관리

전략 자본 150,000원, 1회 매수 수수료 포함 최대 50,000원, 현재 정책의 현금 여유·최대 보유 종목·연속 손실 제한, 일일 실현+현재 평가 손실 3,000원 기준을 검사한다. 금일 평가손익은 당일 가격 변화가 아니라 보유 원가 대비 현재 평가를 포함한다. 수수료는 종목별 주문 가능 정보에서 조회한다. 신규 매수 금액은 손실이나 수익으로 자동 증액하지 않는다. 전략 현금/보유분과 거래소 전체 계좌 자산은 별도다.

계좌/Private WS 최신성·복구 상태·거래 가능 상태·호가 최신성·스프레드·호가 잔량·최소 주문금액을 확인한다. 매도는 매수 손실 차단 조건과 구분해 보유분 범위에서 허용한다. 매수 호가/매도 호가 잔량을 사전 검사하지만 **시장가 체결가격과 최종 수량을 보장하지 않는다.** 연결이 끊기면 프로그램 밖의 거래소 손절을 대신할 수 없다.

외부 거래가 활성화 이후 감지되면 새 주문을 막고 원장 대조와 재활성화를 요구한다. 앱 주문은 실제 체결 ID로 전략 수동 원장에 자동 기록한다. 외부 거래와 과거 보유분을 자동 편입하지 않는다. **앱 주문 체결을 수동 폼으로 다시 입력하면 이중 계산될 수 있으므로 중복 입력하지 않는다.**

## 전송 및 복구

`PrivateClient`는 기존 GET allowlist를 유지한다. 별도 `OrderTransport`만 고정된 `POST https://api.bithumb.com/v2/orders`를 사용한다. 시장가 매수는 `order_type=price, price=총액`, 시장가 매도는 `order_type=market, volume=수량`이다. 문자열 파라미터 직렬화로 SHA512 서명하고 같은 필드를 JSON으로 보낸다. 키·JWT·헤더·API 원문 오류는 노출하지 않는다.

SQLite schema 4의 manual_orders에 고유 client_order_id와 승인 조건을 먼저 저장한다. PREVIEW → SUBMITTING → ACKNOWLEDGED → DONE, REJECTED/UNKNOWN/EXPIRED를 보존한다. 전송 전 BEGIN IMMEDIATE와 미확인 주문 확인으로 다중 탭/프로세스 전송을 직렬화하고 자본을 다시 검사한다. 호출 제한 대기 후 정지·만료·가격을 다시 확인한다. 확정된 입력/인증 거절은 REJECTED, 타임아웃·응답 유실·5xx·알 수 없는 응답은 UNKNOWN이다. 전송은 자동 재시도하지 않는다.

결과가 불명확하면 저장된 거래소 ID 또는 client_order_id로 GET `/v1/order`를 조회한다. 조회 404는 ‘미접수 확정’으로 해석하지 않는다. UNKNOWN/SUBMITTING을 재전송하거나 자동 해제하지 않는다. 미해결 주문이 있으면 신규 주문을 막는다. 원인을 해결할 수 없으면 거래소 앱/고객센터에서 해당 ID를 확인해야 한다. API 장애를 회피하려고 DB 상태를 임의로 수정하지 않는다.

확인된 실제 체결만 원장에 반영한다. 부분 체결은 체결량만 기록하고 주문이 종료될 때까지 추가 주문을 막는다. 미확인 수수료는 0으로 간주하지 않는다. 개별 WS 수수료가 뒤늦게 도착하면 전략 원장의 수수료도 보정한다. 접수 응답만으로 잔고/포지션/손익을 바꾸지 않는다. 정지/긴급 정지는 전송 중이거나 이미 접수된 주문을 취소하지 않는다.

## API

- GET `/api/orders/status`
- POST `/api/orders/activate` — 세션 수동 활성화
- POST `/api/orders/stop` — 새 주문 정지
- POST `/api/orders/preview` — 시장·방향·금액/수량·선택 신호의 확인 내용 생성
- POST `/api/orders/submit` — 저장 ID + 해당 주문 확인 문구, 사용자 최종 확인 경로
- POST `/api/orders/recover` — 조회 복구, 주문 전송 없음

변경 요청은 기존 로컬 Host/Origin/JSON/사용자 지정 헤더 검사를 적용한다. 웹 서버 프록시는 위 경로만 추가 허용한다. 비밀정보 입력 API는 없다. 이 로컬 앱은 외부 공개용 서비스가 아니다.

## 검증과 한계

단위 테스트는 가짜 키·가짜 거래소 MockTransport와 로컬 WebSocket으로 수행한다. 실제 계좌 주문 테스트는 수행하지 않았다. 공식 주문 계약과 클라이언트 ID 조회를 확인했지만 실제 계정 권한·거래소 응답·체결까지의 운영 검증은 사용자가 수행해야 한다. 초기 원장 대조와 외부 체결 등록이 틀리면 전략 성과도 정확하지 않다.
